# ProjectB working guidance

## Task scope and skill selection

- Use skills for the requested operation and the behavior they own; an incidental keyword does not require another skill. The `projectb-*` utility skills are the canonical variants for this repository. Route matching utility requests to those variants; unprefixed personal counterparts are legacy alternatives for other projects. Load only the variant needed for the task.
- Load references only for the current decision. Full-system implementation sequences and test matrices apply to new systems, affected behavior, or the selected acceptance gate; a targeted fix does not require redesigning the subsystem. Preserve every proof required by the gate and invalidate evidence when relevant inputs change.
- Complete authorized implementation, relevant verification, and fixes before reporting completion. Existing explicit approval remains valid within its scope; ask only for a missing consequential decision, newly discovered consequences, expanded scope, unsaved-work conflict, or a permission the tools cannot satisfy.

## Resume the vertical slice efficiently

The gate, candidate, process, and ledger workflow below applies to active vertical-slice implementation and acceptance testing. Documentation, planning, and instruction maintenance use only the references needed for that request.

- When working on the vertical-slice goal, read `AI_Planning/SLICE_STATUS.md`, then run `Scripts/Test/Get-NextIterationBrief.ps1` once for the current candidate, provenance, selected phase, process state, proof gaps, next action, source-snapshot freshness, workflow-helper freshness, and candidate artifact identity. It invokes the contract-aware resume inventory and keeps the complete records on disk. Add `-RefreshSourceSnapshot -RefreshWorkflow` after deliberate source, ledger, contract, snapshot, or helper edits; treat either freshness warning or a candidate identity mismatch as a preflight stop for artifact reuse until its frozen scope is reviewed; use `Get-ResumeBrief.ps1` directly only for a narrower follow-up. Follow the user's pause/resume state.
- A report, planning request, or workflow edit while paused does not resume gameplay implementation. Complete that request, preserve the next action, and wait for the user to resume the goal.
- During active vertical-slice implementation, select one pending acceptance gate at a time and define its expected observable result before editing. After passing a gate or recording a blocker, continue the next authorized gate while the goal is active. Read only its relevant evidence, source, and applicable skills.
- Use `rg` to locate symbols and narrow file ranges. Keep historical reports, full logs, and large skill references out of context unless needed for the current decision.
- Default routine tool output to about 1,500 tokens per call. Filter or summarize on disk first; expand the limit when necessary to understand a failure. Read each applicable skill once per available context and load referenced material only as needed.
- Consult `Scripts/Test/README.md` when running the shared profiles or compact JSON helpers. Preserve full evidence under `Saved/Logs/`; report the outcome, first causal error, and evidence path.
- Build only `LyraEditor` for editor/PIE work and `LyraGame` for packaged-game work as top-level UBT targets. Use `Scripts/Test/Tier1-CompileGate.ps1 -Target <LyraEditor|LyraGame>` and compile only the target needed for the selected phase. Do not use Visual Studio Build/Rebuild Solution, whole-solution MSBuild, all-target builds, or standalone engine test/utility targets. UBT may build dependencies required by the selected project target. This preserves gameplay verification while avoiding regeneration of unused engine-test intermediates.
- Run the cheapest applicable verification first. Compile a coherent set of related C++ fixes, then run affected tests. Package after those checks pass when packaged evidence is required. For a `-skipbuild` package, compile the `LyraGame` target (not only `LyraEditor`) and pass its JSON result to `Scripts/Test/Package-Preflight.ps1 -CompiledTargetRecord`; this prevents staging a stale game binary that cannot resolve newly added runtime classes. When the package runs under restricted permissions, add `-RequireAutomationToolLogWrite` so the engine-side AutomationTool log ACL is proved before Cook/Stage/Pak.
- Treat `Tier1-CompileGate.ps1` `failureSignals` as authoritative alongside the process exit code: bundled .NET/UBT can return process exit 0 after an internal `Result: Failed`/C++ compilation error or a startup `Unhandled exception`, `UnauthorizedAccessException`, access-denied write, or generated-file rename failure. `Package-Preflight.ps1 -CompiledTargetRecord` requires the field to be present and empty, so older records must be regenerated before a package. Do not package a record whose explicit UBT failure signatures are nonempty; preserve the raw compile log and fix the source before retrying. Tier1 canonicalizes relative project inputs against the configured project root before UBT starts and records `projectFileInput`/`projectFileWasRelative`; prefer passing the absolute path directly. After an editor-target compile, confirm the linked runtime DLL timestamp advanced before launching the editor.
- Reuse an existing candidate only when its recorded source, patch, assets, and configuration cover the tested change. Retest passed gates when relevant changes invalidate their evidence; complete the final end-to-end checks.
- Wait on an existing build or test process. Avoid duplicate launches and repeated unchanged log reads. Retry a failure after a change, a new hypothesis, or an explicit reproducibility check.
- After two attempts with the same failure and no new evidence, stop repeating that operation. Record the command, failure, attempted remedies, and condition for retry in the linked evidence document. While the goal is active, continue an independent gate if possible; preserve approval boundaries.
- Prefer structured bridge or CLI inspection where it answers the question. Use fresh UI observations for visual polish, physical input, frontend flow, and security dialogs.
- Put PIE Python inspections inside a function and return only serialized values. Never leave world, actor, widget, or component wrappers in interpreter globals; exceptions must also release them before travel or stopping PIE. If a probe fails with retained objects, clear its references or restart the editor before continuing the travel test.
- Keep progress updates concise and report meaningful changes. After a verified result, update the ledger's gate, evidence, invalidation conditions, and next action; put detailed history in the linked acceptance document.
- Keep the resume ledger under about 100 lines. Store commands and full reports by reference, and replace stale state instead of appending turn histories. Record build/package counts and retry reasons with each gate's evidence to assess workflow overhead.
- Use the gate record in `Scripts/Test/README.md` to preserve the expected result, evidence, retry condition, and next action before a pause or context handoff. Recheck process IDs and artifacts on resume; historical state is not current state.
- Use `Scripts/Test/Get-GateBrief.ps1` after the gate starts to summarize only selected evidence JSON/logs. Keep raw logs on disk and return pass/fail, first causal error, counts, scope, and the evidence path. Consult `AI_Planning/WORKFLOW_EFFICIENCY.md` when measuring or changing workflow efficiency.
- Before an expensive gate, record a compact preflight with source revision, launch paths, process inventory, requested and observed topology, bridge readiness, and UI-channel availability. Stop before launch when the required scope cannot be proved.
- Before an expensive gate with staged/unstaged or untracked inputs, use `Scripts/Test/New-SourceSnapshot.ps1` once to persist the complete tracked patch and untracked manifest; compare its bounded `sourceIdentity` first, then inspect individual hashes or full files only when the identity or a required artifact/configuration check differs. Keep one stable per-gate `source-snapshot-current` path for the resume command and use `-Force` only after deliberate source/ledger edits are complete; use numbered prefixes when immutable attempt history is needed.
- `Get-NextIterationBrief.ps1` compares snapshot text through a BOM-free, normalized-line-ending hash so Windows PowerShell encoding does not create a false freshness warning; the snapshot's original byte hashes and full files remain the audit record.
- Use `Scripts/Test/Start-ProjectBEditor.ps1` for source-built editor launches when the bridge launcher cannot resolve the engine. Reuse the recorded PID and log, and close that editor normally before a rebuild. For a project-local cache directory, pass `-CreateZenDataPath` so a missing Zen path is provisioned during the single `-ValidateOnly`/launch preflight instead of causing a manual retry.
- Cache bridge/reflection capabilities in the gate evidence. Record unsupported operations once and route to a supported inspection path; do not repeat an unchanged unsupported call.
- Advance the same gate manifest after compile, runtime, and package phases. Preserve partial results with explicit `scope`, `proofGaps`, and `nextAction` fields rather than restating them in the ledger.
- Use `Scripts/Test/Set-GatePhase.ps1` to write those phase fields atomically; supply an overall status only when the gate state intentionally changes.
- Restore temporary PIE flags, cheats, fixtures, and input overrides immediately after the run; verify the closed-editor INI before the next gate.
- If Computer Use is unavailable or has no targetable window, record `uiChannel: unavailable` once. Skip only physical/UI assertions and keep structured checks whose scope remains valid.
- For each gate, create one process/evidence contract, reuse its editor/build handles, and stop callbacks in cleanup. Do not redeclare live Python observers or reuse stale UI screenshot state; select, observe, act once, then refresh.
- For hero-dependent combat fixtures, select the loaded primary/melee ability spec by runtime class family, defer sequential activations until the real fire interval completes, and isolate unrelated pawns during relic pass setup; restore every moved transform before marking cleanup complete. Use `Scripts/Test/Get-TeamCombatFixtureBrief.ps1` for one bounded marker read; it recognizes authority, remote-owner, and remote-owner-score marker sets, so do not diagnose remote runs with ad hoc old-marker searches. The remote fixture polls for production damage before pass setup and the score variant samples replicated health/team before the round reset; preserve those bounded waits and exact score-delta markers.
- If editor shutdown reports a forced kill, verify the exact UnrealEditor PID before compiling. Close that known lock owner once and retry the compile only after it exits; do not launch a duplicate editor or repeat an unchanged locked build.
- Treat `hiddenEditorCount` in the resume or gate brief as a stop signal: identify the exact owner and close it normally before launching another editor. Never compensate for a hidden or untargetable process with a duplicate launch.
- Resume briefs are compact by default: use the ProjectB-owned process records and counts first; pass `-IncludeAllProcesses` only when process ownership itself is the active diagnosis. Full records remain in `Saved/Logs/codex-resume-brief.json`.
- For routine resume follow-ups, add `-SummaryOnly` to `Get-ResumeBrief.ps1`; it keeps the full snapshot on disk while returning only the selected gate/process/count projection. Use the full default projection only when ownership or dirty-file detail is the active diagnosis.
- Keep the `**Current candidate:**` line in `AI_Planning/SLICE_STATUS.md` synchronized with the selected gate contract's `candidate`. `Get-ResumeBrief.ps1` reports a warning when they differ; reconcile the two before opening artifact logs or reusing a package so a stale candidate cannot consume another lifecycle.
- After contract/snapshot/candidate metadata edits, use `Scripts/Test/Get-WorkflowValidationBrief.ps1` once for the compact script-parse, JSON-parse, diff, candidate-consistency, and owned-process check. It is workflow hygiene only and never substitutes for compile, runtime, UI, LAN, or acceptance evidence.
- On a gate resume, pass `-GateContractPath <contract> -ContractPhase <compile|runtime|package>` to `Get-ResumeBrief.ps1`; it projects the current gate status, scope, proof-gap count, causal error, retry condition, and next action into the one resume result while preserving the full contract on disk.
- When source provenance is part of the decision, also pass `-SourceSnapshotPath <snapshot>` to `Get-ResumeBrief.ps1`; it adds the stable source identity and individual file hashes to that same bounded resume packet, avoiding a separate snapshot read while keeping the complete files on disk.
- Packaged-flow briefs are count-only by default; request a small event tail only to resolve an ordering question, and use `-OutputJson` when preserving the inventory as gate evidence.
- Runtime presentation helpers should print pass/scope/count/evidence by default and keep peer-level detail in their saved JSON; request verbose output only for a changed diagnosis.
- Gate briefs deduplicate repeated evidence paths and project nested contract details into bounded scalar summaries; use `-ContractPhase compile|runtime|package|all` to select evidence from the gate contract instead of retyping paths. Add `-SummaryOnly` for routine follow-ups so only counts, first causal error, process state, scope, and output path enter context; read the full contract or persisted brief only when a changed diagnosis needs peer-level detail.
- `Get-ResumeBrief.ps1 -SummaryOnly` keeps the full ledger next-action line in `Saved/Logs/codex-resume-brief.json` but bounds the duplicate markdown field in console output; use the contract's `gate.nextAction` for the complete current action and open `fullSnapshot` only when ledger detail changes the diagnosis.
- When a selected phase has no current causal error, persist `firstCausalError: null`; `Get-GateBrief.ps1 -SummaryOnly` treats that explicit value as authoritative instead of resurfacing a stale error from older evidence in the same phase.
- Poll a live log more than once with `Scripts/Test/Get-LogDeltaBrief.ps1` and a gate-owned state file. The first call establishes the offset; later calls report appended errors, critical lines, and requested markers only. Use `-QuietUnchanged` when no transition is expected, `-OutputJson` when the poll is gate evidence, and `-Reset` only after log rotation or for a new evidence file; keep full-log briefs for the acceptance record.
- In separate-process PIE, run `Scripts/Test/Wait-SeparateProcessReady.ps1 -LogFiles <client1>,<client2>,<client3>` once with the target experience before issuing a time-sensitive authority fixture. For staging-to-gameplay commands, also pass `-HostLog <server-log> -HostExperienceMarker <staging-experience>` and, when the starting world matters, `-HostMapMarker <map-name>` so server completion and map selection are gated. When a fixture requires active gameplay, add `-HostRequiredMarker 'BwayRoundManagement: Started playing GAS phase'` (or the exact gate marker) so warmup cannot consume the command. Use `-RequiredMarker` only for an independent child-side prerequisite that is emitted before the authority command; do not use `Local player locked hero` to gate the AutoLock-before-travel flow because that marker is downstream of the command. Use its compact per-child/host `ready`/`timeout` result; preserve captured logs and change the readiness hypothesis after a timeout instead of hand-polling or relaunching unchanged.
- For packaged four-process transport fixtures, give clients the result-screen test-exit trigger and keep the listen host alive until every client has reached that trigger; a host `PostMatch` test-exit can close the connection while a slower client is still processing replicated results. Terminate the host during owned fixture cleanup and record that teardown separately from client gameplay/error status.
- When a staged fixture combines a network cvar with a development console command, pass separate `-ExecCmds` arguments and preserve both in the runner's recorded argument list; a semicolon-delimited value can start the process while dropping the time-sensitive fixture dispatch. For authority fixtures issued during startup, wait for the exact `Playing` phase before selecting or moving actors. Keep the retry bounded, and preserve an unclassified asset warning in the brief rather than relabeling it as startup noise.
- Persist the packaged transport harness verdict as compact JSON before returning, with host readiness, client exit status, and owned host teardown as separate fields. On resume, read that result plus one count-only packaged-flow brief; do not reconstruct a truncated console verdict from raw logs or relaunch an unchanged candidate.
- For packaged shop probes, do not use an immediate `-ExecCmds=ToggleUpgradeShop` as UI evidence because command-line execs can run before the local controller exists. Use the development-only delayed `bway.Test.ShopOpenAndBuy` probe for structured widget/RPC coverage, verify the catalog's actual stable ID, and keep physical B-key/gamepad input as a separate acceptance gate.
- For a packaged client probe launched from startup `ExecCmds`, use a no-world delegate and one bounded ticker to resolve the post-travel gameplay world before starting timers. Keep expected wallet assertions data-derived from the loaded catalog and an immediate baseline, with a documented bounded passive-income tolerance. Verify after `ProcessEvent` through weak widget references or a freshly resolved world; never schedule a post-action callback through a raw world pointer that may be tearing down.
- Match wrapper markers against emitted log categories such as `LogTemp: .*` or `LogExit: .*`; command-line arguments can contain the same test-exit text and must not satisfy a pass pattern.
- After an owned packaged shop run, use `Scripts/Test/Get-PackagedShopProbeBrief.ps1` with the host/client logs and candidate snapshot to persist one compact, data-derived result. This is an evidence extraction step and does not justify relaunching or recooking a candidate whose artifact identity still matches.
- For a second readiness checkpoint in the same PIE attempt, pass `-BaselineJson <staging-readiness.json>` so polling begins at the prior byte offsets; this prevents reused `ProjectB*.log` markers from satisfying a destination experience.
- After the explicit staging-map load and before PIE starts, create a byte baseline with `New-LogOffsetBaseline.ps1` and pass its JSON as `-BaselineJson` to the first readiness checkpoint; this prevents stale markers in reused child logs from satisfying staging readiness. A baseline records offsets only and cannot satisfy readiness.
- After a separate-process readiness timeout, run `Scripts/Test/Get-SeparateProcessTravelBrief.ps1` once on the captured child logs and host log. Use bounded transition counts to select the next hypothesis; inspect narrow raw ranges only when those counts identify a changed diagnosis.
- Use `Scripts/Test/Tier1-CompileGate.ps1 -OutputJson <path>` to persist source revision, runner, process, exit, elapsed, and log metadata immediately after a build. This avoids reconstructing compile evidence from console output while preserving the same compile gate.
- Treat a compile record with `status: running` as an owned in-progress gate. Wait for its recorded process before reading compiler output; Tier1 publishes the final record atomically so a partial JSON read cannot trigger a redundant compile.
- Use `Scripts/Test/Run-AutomationTests.ps1 -TestFilter <prefix> -OutputPrefix <fresh-base>` for headless automation filters. Pass `-ForceMemoryDDC` on this source engine when the default DDC has no writable node; the helper owns one editor PID, refuses stale report directories, and requires report success, the framework exit marker, and process exit 0.
- Use `New-AcceptanceSummary.ps1 -SummaryOnly -OutputJson <path>` when startup screening is needed but per-log rows are not part of the changed diagnosis; the complete report remains persisted.
- Treat the recurring Zen security-configuration message as known nonfatal only when the compact brief classifies it. Keep Pixel Streaming target-window errors actionable for rendered/UI gates; the authority-only combat fixture may classify that message in its own scope. Preserve total error counts, unknown-error counts, and critical lines; never suppress an unclassified error.
- Give each observer one declared timeout and cleanup owner. If it times out without the expected transition, record the partial result and change the observation point or fixture before retrying; do not repeat the same callback against unchanged source and evidence.
- Summarize repeated attempts with `Scripts/Test/Get-RunFamilyBrief.ps1` before inspecting individual logs. Use the family counts and error signatures to decide whether a retry changes the hypothesis; load only the latest or causally relevant log afterward.
- For settled separate-process replication, use `Scripts/Test/Get-ReplicationGateBrief.ps1` once after readiness and fixture collection. It joins readiness, authority fixture, and multi-sample peer evidence into one bounded record and persists the detailed child briefs; use `-IncludeSamples` only for a changed diagnosis. When health can regenerate, omit fixed expected health and compare each child sample with its paired authority sample within a bounded tolerance (use 20 health points for the remote-owner lag fixture) while requiring exact team equality. Issue adverse latency as `Net PktLag=100`; the space form is invalid. Capture child logs before teardown, and require the remote fixture's `COMPLETE` or `RemoteScore COMPLETE` marker before promoting the result; its target hold, damage poll, pre-score sampling, and extended verifier are development-only cleanup-scoped aids and do not change shipping gameplay. If Unreal rotates a reused child log, archive the three files and create a new baseline rather than retrying against stale offsets.
- For remote-owner fixtures, apply multiprocess PIE settings before editor launch and dispatch time-sensitive commands to the authority PIE world. The native editor console route targets the editor world in this topology; cache the `EditorLevelLibrary.get_pie_worlds(False)`/`SystemLibrary.execute_console_command` fallback once per editor lifecycle, keep the source and target world in preflight evidence, and preserve `uiChannel: unavailable` when Computer Use cannot target a window.
- In this engine bridge's Python surface, PIE `World` wrappers do not expose `get_net_mode`; for the configured four-world listen topology, use the first `EditorLevelLibrary.get_pie_worlds(False)` world as the authority and record that capability once. Do not probe the unsupported method repeatedly or treat its failure as gameplay evidence.
- Development console fixtures invoked through the bridge should use a no-world delegate and resolve the intended authoritative or client PIE world internally when the topology is known. Record a missing world as setup failure and fix dispatch once; do not spend another lifecycle retrying the editor-world invocation.
- For short-lived four-world PIE fixtures, prefer one command sequence with explicit settling samples (for example 0.5 and 2.0 seconds). Preserve the transient sample and require the settled all-peer result before marking convergence; use one bounded log extraction for the decision.
- For buildable round-reset diagnostics, call the production `ResetRoundState` plus each `ABwayPlayerState::BeginRoundStatTracking` in the development fixture when phase timing is unstable. Evaluate persistent actor count and per-round quota independently; do not claim a `StartRound` transition when the orchestrator is not in Playing.
- For placement ability cleanup, a cancel fixture may reuse an already active placement spec before issuing `LocalInputCancel`. A no-hit confirm is an invalid-target probe and should remain active with quota unused until a valid target is submitted; physical valid-confirm proof remains a separate gate.
- After a buildable fixture, run `Scripts/Test/Get-BuildableFixtureBrief.ps1` once with the saved editor log. Use its compact pass fields, peer counts, malformed-submission results, and first fixture error for routine decisions; expand `-IncludeSamples` or raw log ranges only when the brief identifies a changed replication diagnosis. Pass a bare filename beside the log or an explicit path containing a directory; the helper resolves either form without a nested-path retry.
- After a completed-match rematch fixture, run `Scripts/Test/Get-MatchUpgradeLifecycleBrief.ps1` once with the saved editor log. Use its setup/request/verify/PASS markers, setup-blocked state, and error counts for routine decisions; inspect raw ranges only when the compact lifecycle result changes the diagnosis. This proves only same-process production rematch reset, so packaged LAN and physical shop evidence remain separate.
- For buildable authoritative rejection, issue `bway.Test.BuildableReplicatedQuotaReject` after `bway.Test.AutoLockAllHeroes`. It waits for Playing plus the client/authority ownership chain, sends target data through GAS under `Net PktLag=100`, requires an authority callback with no spawn and a clean ability end, and restores the quota; this does not replace physical valid-target proof.
- When physical input is unavailable, `bway.Test.BuildableReplicatedValidConfirm` can prove the synthetic client-to-server target-data path: require authoritative acceptance, one spawned buildable, four-world convergence, clean ability end, and fixture-owned actor cleanup. Keep physical cursor selection and packaged UI/LAN as separate proof gaps.
- Shared evidence helpers keep bounded compatibility aliases for prior parameter names; use the documented invocation once rather than probing alternate names.
- Save repeated diagnostic procedures as parameterized scripts after they prove useful. Do not build a new framework for a one-off check, reread an entire skill catalog, or repeat a passed check without a relevant invalidation reason.
- Preserve unrelated work. Consult `Plugins/GameFeatures/BreakawayCore/Docs/Agent_Testing_Ladder.md` when building, restarting the editor, or collecting multiplayer evidence.

Efficiency changes must preserve the target: final-public-alpha Breakaway gameplay parity, integrated placeholder art, and a working four-player listen-server LAN flow. Startup screening, headless runs, and same-process PIE each prove only their recorded scope.
